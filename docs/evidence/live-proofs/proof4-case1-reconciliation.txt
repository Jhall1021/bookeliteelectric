4. WHAT PHASE B ACTUALLY CLAIMS

   From the implementation's own header:

     "...only decides whether an existing, READY, GitHub-built deployment of the
      CURRENT main may take THE CANONICAL DOMAINS — and then says so explicitly
      with `vercel promote`, because auto-assignment is off on the canonical
      project and NOTHING ELSE MOVES THOSE DOMAINS."

   The claim is about the canonical domains, and only those. It does not claim
   that every generated URL stays on the incumbent, and no code enforces such a
   claim.

   THEREFORE CASE 1 DOES NOT CONTRADICT THE PHASE B SAFETY PROPERTY. Two
   generated aliases moved; no canonical customer-facing host moved, because
   none exists on this project; and the production target did not move.

   MY EARLIER FRAMING WAS WRONG. I wrote that "creation at target production is
   not inert", that "the window in which a candidate is built but not yet
   serving does not exist for these aliases", and that verify-then-promote
   "would be verifying something that is already live". The first is true only
   of generated aliases. The second and third silently substituted generated
   aliases for the hosts the release governs, and on the hosts it governs the
   window is intact. I generalised from the hosts I could see to the hosts the
   design is about.

5. autoAssignCustomDomains: false — THREE KINDS OF STATEMENT, KEPT APART

   DOCUMENTATION (reported by the operator; I have NOT independently verified it
   against Vercel's documentation in this session): Vercel distinguishes
   generated *.vercel.app URLs from custom production domains, and a staged
   deployment may hold generated URLs while custom-domain assignment is withheld
   until promotion.

   CODE ASSUMPTION (verifiable, and verified above): the release assumes
   auto-assignment is off on the canonical project so that nothing but an
   explicit promote moves the canonical domains. It never reasons about
   generated aliases at all.

   LIVE OBSERVATION (this project, this session): autoAssignCustomDomains is
   false; the project has NO custom domains; two generated aliases moved on
   creation; the shortest project alias and the production target did not.

   WHAT IS NOT ESTABLISHED: how a CUSTOM domain behaves on creation under
   autoAssignCustomDomains: false. This project has none, so nothing here tests
   it. The documentation and the code assumption agree that it should not move;
   both are claims, and neither has been observed. That is proof 6's question.

6. WHAT CASE 1 REQUIRES

   NOT a code or design correction. The implementation already restricts itself
   to the three canonical hosts, and the behaviour observed falls entirely
   outside them.

   A NARROWER STATEMENT OF THE GUARANTEE, plus an evidence note:

     Phase B's property is "no CANONICAL CUSTOMER-FACING HOST moves before
     Phase C", not "no Vercel-generated alias moves". Creating a
     production-target deployment DOES move generated branch and project+scope
     aliases, and does NOT move the production target.

   The evidence note belongs with case 1's record so the raw finding is never
   read on its own. The correction in section 4 is the substance of it.

7. CAN CASE 2 PROCEED SAFELY UNDER THE EXISTING BOUNDARY

   On this evidence, yes, with the same bracketing.

   Expected path: the guard refuses SHA_NOT_MAIN, the && chain stops, the build
   ERRORs, and the deployment never reaches READY. Generated aliases attach to
   READY deployments — dpl_2zZV, proof 5's ERROR build, took none — so a
   refusing build should move nothing at all. Case 2 is expected to be quieter
   than case 1, not louder.

   THE FAILURE MODE WORTH NAMING. If the guard does NOT refuse — the very thing
   case 2 tests — the deployment would reach READY and would then take the two
   generated aliases, as case 1's did. Those would point at a build of
   afa2915…, which is this same fixture minus one README line. The production
   target would remain dpl_8uZb, which is itself afa2915…. So the worst case is
   two generated aliases on a disposable project serving near-identical content,
   and a significant finding recorded.

   ONE IMPROVEMENT WORTH MAKING FIRST, and it is the operator's call: capture
   targets.production in the before/after snapshots. Case 1 needed that field to
   be reconciled and I had to reason around its absence. Case 2 should not need
   the same reasoning. That is a change to capture-state.sh, which this
   authorization does not cover.
